# /suspend-work

引数: 要約を書く Issue 番号（省略可）。省略したら、ブランチ名 `feature/issue-{番号}-...` から番号を読む。

目的は 2 つある。作業の状態を失わないこと（保存・コミット・push）と、**このセッションが再開できなくても引き継げる要約を残すこと**。要約は Issue のコメントに書く。スマホやクラウドのセッションからも読め、Issue の履歴にも残るため。

Unity と Blender は閉じない（保存だけする）。強制終了（`Stop-Process` など）もしない。

## 手順

1. **作業を区切りのよいところで止める**
   - 編集の途中なら、ファイルが壊れていない状態（構文が閉じている状態）まで進めてから止める。新しい作業は始めない
   - 実行中のバックグラウンドのタスクと `Monitor` を止める（`TaskList` で確かめて `TaskStop`）。止めると困るもの（長いビルドなど）は止めずに、要約の「途中の作業」に書く
   - 人間の承認待ちや判断待ちになっている事項を控えておく（要約の「判断待ち」に書く）

2. **Unity の状態を片付ける**（Editor が起動している場合）
   - `editor_status` で Play 中なら `editor_stop` で止める
   - `list_open_scenes` で `isDirty` を確かめる。dirty なシーンは CLAUDE.md の「デバッグ実行」の手順 2 で扱う（意図した変更なら `save_scene`、意図しない変更なら保存せずに `EditorSceneManager.OpenScene(path)` で開き直して破棄する）。判断できないときは保存も破棄もせず、要約の「判断待ち」に書く
   - `console_status` でコンパイルエラーの件数を確かめる。エラーがあれば要約の「途中の作業」に書く（直そうとしない）

3. **Blender の状態を片付ける**（起動している場合）
   - MCP（`execute_blender_code`）で `bpy.ops.wm.save_mainfile()` を実行して `.blend` を保存する。`bpy.data.is_dirty` は MCP での変更を反映しないので、確かめずに毎回保存する
   - 無題のファイル（`bpy.data.filepath` が空）のときは、保存先を推測しない。人間に保存先を尋ねる。答えが無ければ要約の「判断待ち」に書く
   - 開いている `.blend` のパスを控えておく（要約の「再開の手順」に書く）

4. **git の状態を残す**（コマンドは 1 回に 1 つずつ実行する。CLAUDE.md の「作業上のルール」）
   - `git status --short` と `git branch --show-current` で状態を確かめる
   - **main の上にいるときはコミットしない**。変更の内容を要約に書いて、人間に知らせる
   - 作業と関係ない差分はコミットしない。Unity が自動で変えた `unity/ProjectSettings/` や、自動再シリアライズだけのシーンの差分などのこと。どれが作業の差分かわからないときも、コミットせずに要約に書く
   - 作業の差分を `git add <ファイル>` でファイルを指定して加える（`git add -A` / `git add .` は使わない）。新規アセットの `.meta` も含める
   - コミットメッセージは scratchpad に Write で書き、`git commit -F <ファイル>` でコミットする。1 行目は `WIP: <何の途中か>` にする（例: `WIP: ハイパーブーストの衝撃波の減衰を調整中`）。本文に、要約の「途中の作業」を 1〜3 行で書く
   - `git push -u origin <ブランチ名>` で push する。失敗したら 1 回だけ再試行し、それでも失敗したら要約に「未 push」と書く
   - WIP のコミットは、再開した後で取り消したり（`reset`）書き換えたり（`amend`）しない（強制 push が要るため）。そのまま上に続けてコミットする

5. **要約を書いて Issue にコメントする**
   - 下の「要約の形式」で、scratchpad の `suspend-summary.md` に Write で書く
   - `gh issue comment <番号> --repo star-globe/OWMechTest --body-file <ファイル>` で投稿する
   - Issue 番号がわからない（引数もブランチ名にも無い）ときは、ブランチの PR があればその PR にコメントする（`gh pr comment <番号> --repo star-globe/OWMechTest --body-file <ファイル>`）。PR も無ければ、どこに書くかを人間に尋ねる。答えが無ければ、scratchpad のファイルのパスを報告して終わる
   - 投稿に失敗したら、要約の全文を最後の返答に書く（会話の記録に残す）

6. **報告する**
   - コメントの URL、push したブランチとコミット、片付けられなかったこと（判断待ち・未 push など）を 3〜5 行で返す
   - 自分が作業用セッション（子）なら、同じ内容を `send_message` で親セッションにも送る。送り先は、親セッションのポリシー（`docs/management-session-policy.md` の 8 章）にある親の ID だけにする

## 要約の形式

新しいセッションがこのコメントだけを読んで再開できるように書く。会話の流れを知らない人にもわかる言葉で書き、「さっきの」「例の」などは使わない。完了した作業の経緯は短くする（PR やコミットを見ればわかる）。

1 行目は `## 中断時の引き継ぎ` で始める（`/resume-work` はこの見出しでコメントを探す）。

```
## 中断時の引き継ぎ（YYYY-MM-DD HH:MM）

- ブランチ: feature/issue-XX-xxx（最後のコミット: <短いハッシュ> <1 行目>、push: 済み / 未）
- PR: #XX（無ければ「なし」）
- セッション: <自分のセッション ID がわかれば書く>

### 終わったこと
- （箇条書き。1 項目 1 行）

### 途中の作業
- （どのファイルのどこまで進んだか。動かない状態なら、何が動かないか）

### 次の一手
1. （再開したセッションが最初にやること。具体的に）
2.

### 判断待ち・注意点
- （人間に聞くこと、保存も破棄もしなかったシーン、コミットしなかった差分、試して駄目だったこと）

### 再開の手順
- `git switch feature/issue-XX-xxx` してから `git pull`
- Unity: 開くシーン（あれば）
- Blender: 開く `.blend` のパス（あれば）
```
