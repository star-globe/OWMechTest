# /run-worker

各マシンの管理用セッション（3 層の 2 層目）の手順。運用の決まりは `docs/management-session-policy.md` の「7」「8」「10」。

引数: Issue 番号（`$ARGUMENTS`）。無ければ、指示の中の Issue 番号を使う。それも無ければ人間に尋ねる。

このセッションでは実装・調査・Unity / Blender の操作をしない。作業フォルダを作業用セッションと共有するので、ブランチを切り替えない。

## 1. 準備

- `get_session` を引数なしで呼び、自分のセッション ID と `environment_id` を控える
- このマシンで、自分の作った作業用セッション（`parent:<自分の ID>` タグ）が承認待ち・作業中なら、新しく作らずに人間（またはクラウドの管理用セッションへの返答）でその旨を伝えて止まる
- 作業フォルダが main で、未コミットの変更が無ければ `git pull` で最新にする（main 以外なら切り替えずにそのまま進める）

## 2. 作業用セッションを作る

`create_session` を次のように呼ぶ。

- `environment_id`: 自分の `environment_id`（このマシン）
- `title`: `OWMechTest-<担当>-Issue<番号>`
- `tags`: `["parent:<自分の ID>"]`
- `append_system_prompt`: 下の「親セッションの明示」のブロック
- `prompt`: 「親セッションの明示」のブロック + 下の「依頼」のひな形

### 親セッションの明示

`docs/management-session-policy.md` の「8」のブロックを、`<親の ID>` を自分の ID に置き換えてそのまま使う。

### 依頼

```
## 依頼
Issue #<番号>「<タイトル>」を担当してください。

1. `/issue-start <番号>` で着手し、実装方針（ラベル・他 Issue との競合・依存を含む）を提示したら、人間の承認を待つ
2. 承認後は、実装 → `/unity-verify`（必要なら `/unity-verify play`）→ コミット → push → PR の作成まで進める。マージはしない
3. ブランチは `git switch -c feature/issue-<番号>-<内容>` で作る（`git checkout` は使わない）
4. 次の時点ごとに、結果を 3〜5 行にまとめて親（<自分の ID>）へ `send_message` で送る: 方針を提示したとき／PR を作成したとき／作業が終わったとき／判断を求めて止まったとき
<Design の場合: Design の PR にはスクリーンショットを 1〜3 枚載せる。Blender に送るコードの先頭に目的を 1〜2 行のコメントで書く>

仕様が変わる場合は CLAUDE.md の「仕様の変更」に従い、`docs/spec/` の差分案を示して了承を得てから編集してください。
```

クラウドの管理用セッションの指示に追加の条件（進めてよい段階など）があれば、依頼に足す。

## 3. 報告する

- **クラウドの管理用セッションへは `send_message` を送らない**（`elevated_session_untrusted_device` で拒否される）。人間に報告文の貼り付けも頼まない
- 作業用セッションを作ったとき、作業用セッションから報告を受けたときは、要点を 3〜5 行でこのセッションの最後の返答に書く。1 行目は「【報告】<自分の ID>：#<番号> <件名>」とする。クラウドの管理用セッションが `list_events` で読みに行く
- 作業用セッションが人間の承認を待っているときは、何を待っているか（方針の承認、コマンドの承認など）と、claude.ai で開くセッションの名前を書く

## 4. 作業用セッションから報告が来たとき

- 1 行目の送り元が自分の作った作業用セッションかを確かめる
- 内容を 3 の形式で最後の返答に書く。作業用セッションへの追加の指示は、クラウドの管理用セッションか人間から頼まれたときだけ送る（先頭に「報告先: <自分の ID>」を書く）
- PR が作成されて作業が終わったら、次の Issue には自分から着手しない。クラウドの管理用セッションの指示を待つ
