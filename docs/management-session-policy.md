# 管理用セッションのトークン節約ポリシー

管理用セッション（作業用セッションを作って Issue を進めさせ、PR やタスクを管理するセッション）の使用量を抑えるための決まり。

## 背景

- 会話の内容（ツールの出力を含む）は、ターンごとにすべて読み直される。そのため、一度読み込んだ大きな出力は、その後のターンでも毎回コストがかかる
- 2026-11-10 には、管理用セッションの会話が長くなったことで 1 日に約 $10 を使い、作業用セッションも使用量の上限で止まった

## 1. 役割を分ける

- 管理用セッションでは、指示、状態確認、PR の作成とレビュー対応、Issue とチェックリストの更新だけを行う
- 実装、調査、Unity / Blender の操作は作業用セッションに任せる。管理用セッションで直すのは、ドキュメントや設定の数行程度の小さな変更に限る
- サブエージェント（Agent ツール）は、人間に指示されたときだけ使う

## 2. 作業用セッションの状態を確認する

- `get_session` の要約（post_turn_summary）で確認する。普段はこれで足りる
- 詳しく知る必要があるときだけ `list_events` を使う。`kinds: ["assistant", "result"]` などで絞り、`limit` は小さくする。絞らずに読むと、起動時のツール一覧などで大量のトークンを使う
- 定期的に確認しない（短い間隔の `ScheduleWakeup` やループは使わない）。人間に聞かれたとき、または作業用セッションから報告が来たときに確認する
- `send_message` で指示を送るときは、作業の終わりに「結果を 3〜5 行で報告する」よう頼む。管理用セッションは、その報告と `get_session` だけで状況を判断できるようにする

## 3. 大きな出力を読み込まない

- ファイルは必要な範囲だけ読む（Read の `offset` / `limit`、Grep の `head_limit`）。ファイル全体を読むのは、編集する前に必要なときだけにする
- `git diff` や `gh pr diff` は、まず `--stat` で変更の規模を見てから、必要なファイルだけを表示する
- `gh` の出力は `--json` と `--jq` で、必要な項目だけに絞る
- `get_scene_hierarchy`、`console`、`list_tests` などの出力が大きい MCP ツールは、管理用セッションでは使わない（作業用セッションで使う）
- コマンドの出力は `tail` / `head` で末尾や先頭だけにする

## 4. 返答を短くする

- 返答では結果と次の判断材料だけを書き、ツールの出力をそのまま貼らない
- 確認済みのことを繰り返し説明しない

## 5. 会話を区切って新しいセッションにする

- 次のどれかに当てはまったら、新しい管理用セッションに引き継ぐよう人間に提案する
  - PR のマージや Issue の完了など、作業に区切りがついた
  - 大きな出力（長い diff やログなど）を何度か読み込んだ
  - 話題が別の Issue に移る
- 引き継ぐときは、下の形式で要点だけを書く。経緯や完了した作業の詳細は書かない（必要なら PR、Issue、作業ログを見ればわかる）

```
## 現在の状況（YYYY-MM-DD 時点）
- 進行中: Issue #XX（担当セッション ID、ブランチ名、今どこまで進んだか、止まっている理由）
- レビュー待ちの PR: #XX（内容を 1 行で）
- 人間の判断待ち・保留: （項目と理由を 1 行で）

## 運用上の注意
- （このポリシーやメモリに無い、今回だけの注意点）
```

## 6. Blender のコマンドを評価して解説する

作業用セッションが Blender のコマンドの承認を求めてきたときに、人間が内容を判断しにくい場合がある。対象は、Blender MCP の `execute_blender_code` などで送る Python のコードと、`tools/blender/export.sh` などのコマンド。こうした承認について人間に頼まれたら、管理用セッションが内容を評価して解説する。

- 承認待ちのコマンドは、`list_events` で作業用セッションの最新の `assistant` のイベントを読んで取り出す（`kinds: ["assistant"]`、`limit` は 5 程度）。解説に必要な範囲だけを読む
- 次の項目を、短く日本語で解説する
  - **何をするか**: 作成・変更・削除するオブジェクト、メッシュ、マテリアルなど
  - **ファイルへの書き込み**: `.blend` の保存先、FBX のエクスポート先（`unity/Assets/Models/` に書き出すと Unity が取り込んで `.meta` ができる）、それ以外のファイル
  - **元に戻せない操作**: 削除、上書き保存、`orphans_purge` など
  - **ポリシーに合っているか**: `docs/modeling-work-policy.md`、`docs/blender-unity-pipeline.md` の命名規約とマテリアルスロット、試しのエクスポートでは `base_path` に scratchpad を指定しているか
  - **判断**: 承認してよい / 直してから実行させる / 拒否する、のどれかとその理由
- 直す必要があれば、`send_message` で作業用セッションに直す点を伝える。管理用セッションでは Blender のコマンドを実行しない
- 評価しやすくするため、作業用セッションには、Blender に送るコードの先頭に、目的をコメントで 1〜2 行書くよう頼む
