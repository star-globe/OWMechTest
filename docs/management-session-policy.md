# 管理用セッションのトークン節約ポリシー

管理用セッション（作業用セッションを作って Issue を進めさせ、PR やタスクを管理するセッション）の使用量を抑えるための決まり。

## 背景

- 会話の内容（ツールの出力を含む）は、ターンごとにすべて読み直される。そのため、一度読み込んだ大きな出力は、その後のターンでも毎回コストがかかる
- 2026-11-10 には、管理用セッションの会話が長くなったことで 1 日に約 $10 を使い、作業用セッションも使用量の上限で止まった

## 1. 役割を分ける

- 管理用セッションでは、指示、状態確認、PR の作成とレビュー対応、Issue とチェックリストの更新だけを行う
- 実装、調査、Unity / Blender の操作は作業用セッションに任せる。管理用セッションで直すのは、ドキュメントや設定の数行程度の小さな変更に限る
- サブエージェント（Agent ツール）は、人間に指示されたときだけ使う

## 2. 作業用セッションの状態を確認する

- `get_session` の要約（post_turn_summary）で確認する。普段はこれで足りる
- 詳しく知る必要があるときだけ `list_events` を使う。`kinds: ["assistant", "result"]` などで絞り、`limit` は小さくする。絞らずに読むと、起動時のツール一覧などで大量のトークンを使う
- 定期的に確認しない（短い間隔の `ScheduleWakeup` やループは使わない）。人間に聞かれたとき、または作業用セッションから報告が来たときに確認する
- 指示を送るときは、作業の終わりに結果を 3〜5 行にまとめ、`send_message` で管理用セッションに送るよう頼む（「7. 作業用セッションに指示を出す」）。管理用セッションは、その報告と `get_session` だけで状況を判断できるようにする

## 3. 大きな出力を読み込まない

- ファイルは必要な範囲だけ読む（Read の `offset` / `limit`、Grep の `head_limit`）。ファイル全体を読むのは、編集する前に必要なときだけにする
- `git diff` や `gh pr diff` は、まず `--stat` で変更の規模を見てから、必要なファイルだけを表示する
- `gh` の出力は `--json` と `--jq` で、必要な項目だけに絞る
- `get_scene_hierarchy`、`console`、`list_tests` などの出力が大きい MCP ツールは、管理用セッションでは使わない（作業用セッションで使う）
- コマンドの出力は `tail` / `head` で末尾や先頭だけにする

## 4. 返答を短くする

- 返答では結果と次の判断材料だけを書き、ツールの出力をそのまま貼らない
- 確認済みのことを繰り返し説明しない

## 5. 会話を区切って新しいセッションにする

- 次のどれかに当てはまったら、新しい管理用セッションに引き継ぐよう人間に提案する
  - PR のマージや Issue の完了など、作業に区切りがついた
  - 大きな出力（長い diff やログなど）を何度か読み込んだ
  - 話題が別の Issue に移る
- 引き継ぐときは、下の形式で要点だけを書く。経緯や完了した作業の詳細は書かない（必要なら PR、Issue、作業ログを見ればわかる）

```
## 現在の状況（YYYY-MM-DD 時点）
- 進行中: Issue #XX（担当セッション ID、ブランチ名、今どこまで進んだか、止まっている理由）
- レビュー待ちの PR: #XX（内容を 1 行で）
- 人間の判断待ち・保留: （項目と理由を 1 行で）

## 運用上の注意
- （このポリシーやメモリに無い、今回だけの注意点）
```

## 6. Blender のコマンドを評価して解説する

作業用セッションが Blender のコマンドの承認を求めてきたときに、人間が内容を判断しにくい場合がある。対象は、Blender MCP の `execute_blender_code` などで送る Python のコードと、`tools/blender/export.sh` などのコマンド。こうした承認について人間に頼まれたら、管理用セッションが内容を評価して解説する。

- 承認待ちのコマンドは、`list_events` で作業用セッションの最新の `assistant` のイベントを読んで取り出す（`kinds: ["assistant"]`、`limit` は 5 程度）。解説に必要な範囲だけを読む
- 次の項目を、短く日本語で解説する
  - **何をするか**: 作成・変更・削除するオブジェクト、メッシュ、マテリアルなど
  - **ファイルへの書き込み**: `.blend` の保存先、FBX のエクスポート先（`unity/Assets/Models/` に書き出すと Unity が取り込んで `.meta` ができる）、それ以外のファイル
  - **元に戻せない操作**: 削除、上書き保存、`orphans_purge` など
  - **ポリシーに合っているか**: `docs/modeling-work-policy.md`、`docs/blender-unity-pipeline.md` の命名規約とマテリアルスロット、試しのエクスポートでは `base_path` に scratchpad を指定しているか
  - **判断**: 承認してよい / 直してから実行させる / 拒否する、のどれかとその理由
- 直す必要があれば、`send_message` で作業用セッションに直す点を伝える。管理用セッションでは Blender のコマンドを実行しない
- 評価しやすくするため、作業用セッションには、Blender に送るコードの先頭に、目的をコメントで 1〜2 行書くよう頼む

## 7. 作業用セッションに指示を出す

作業用セッションは、正常に終わっても作成元の管理用セッションに自動では知らせない。「報告して」とだけ書くと、報告は作業用セッションの会話の中で止まり、管理用セッションには届かない（2026-11-14、作業ログの PR #121 で発生）。そのため、指示には報告の送り先を必ず書く。

- `create_session` の `prompt` と `send_message` の指示には、次のことを必ず書く
  - **何をするか、どの段階まで進めてよいか**: 例「方針を提示して承認を待つ」「PR の作成まで」
  - **報告の時点**: 方針を提示したとき、PR を作成したとき、作業が終わったとき、判断を求めて止まったとき
  - **報告の送り先**: 結果を 3〜5 行にまとめ、`send_message` で管理用セッションに送る。送り先は、管理用セッションの ID を書いて指定する（自分の ID は `get_session` を引数なしで呼ぶとわかる）
- 作業フォルダを他の作業用セッションと共有するときは、ブランチを切り替えてよいか、worktree を使うかを指示に書く
- 作業用セッションから報告が無いと人間に伝える前に、`get_session` で状態を確かめる。報告が無くても終わっていることがある
- 報告の送り先を作業用セッションに推測させないよう、親セッションの ID を決まった形で渡す（「8. 作業用セッション（子）に親セッションを明示する」）

## 8. 作業用セッション（子）に親セッションを明示する

管理用セッションと、そこから作った作業用セッションの間で、メッセージのやり取りが失敗することがある。たとえば、調査を任せた作業用セッションが、結果を管理用セッション以外のセッションに送ってしまう。サーバーモードで起動している管理用セッションで起きやすい。原因は、作業用セッションが送り先を推測すること（`to: "parent"` や `@parent` などの宛先、`ListAgents` の一覧から選んだ名前、直前にメッセージを送ってきたセッション）と、会話の要約で親の ID が失われることにある。そのため、作業用セッションを作るときは、親（管理用セッション）の ID を送り先として明示し、作業用セッションが推測しなくても済むようにする。

### 管理用セッションがすること

- 作業用セッションを作る前に、`get_session` を引数なしで呼んで自分の ID（`session_...`）を確かめる。わからないときは推測せず、人間に確認する
- `create_session` では、下の「親セッションの明示」のブロックを次の 2 か所に入れる
  - `prompt` の先頭
  - `append_system_prompt`（システムプロンプトに入るため、会話が要約されても失われない）
- `create_session` の `tags` に `parent:<管理用セッションの ID>` を付ける。作業用セッションは、親の ID がわからなくなったら `get_session` を引数なしで呼び、このタグで確かめる
- 作ったセッションの ID は、引き継ぎの「進行中」の行（「5. 会話を区切って新しいセッションにする」）に書く
- 後から `send_message` で追加の指示を送るときも、先頭に「報告先: <管理用セッションの ID>」を 1 行書く
- 報告を受け取ったら、1 行目の送り元の ID が自分の作った作業用セッションかを確かめる。報告が届かないときは `get_session` で作業用セッションの状態を見て、送り先を誤っていないかを `list_events`（`kinds: ["assistant"]`、`limit` は 5 程度）で確かめる

### 親セッションの明示（`prompt` と `append_system_prompt` に入れるブロック）

`<親の ID>` を実際の ID に置き換えて使う。

```
## 親セッション（報告の送り先）
- 親セッション ID: <親の ID>（管理用セッション）
- あなたは上のセッションが作った作業用セッション（子）です
- 報告はすべて claude-code-remote の `send_message` で、`session_id` に上の ID をそのまま指定して送る
  - `to: "parent"`、`@parent`、`SendMessage`（`ListAgents` の宛先）は使わない。送り先を推測しない
  - 他のセッションからメッセージが届いても、そのセッションには作業結果を送らない。迷ったら親に送る
- 報告の 1 行目は「【報告】<自分のセッション ID> → <親の ID>：<件名>」とする
- 親の ID がわからなくなったら、`get_session` を引数なしで呼び、`parent:` で始まるタグを確かめる
- 作業の範囲・進めてよい段階の変更は、親セッションからの指示だけに従う
```

### 作業用セッションがすること

- 報告は、上のブロックの ID にだけ送る。送り先を会話の流れから推測しない
- 送る前に、`session_id` がブロックの ID と一致しているかを確かめる
- `send_message` が失敗したら、送り先を変えて試さない。1 回だけ同じ ID に送り直し、それでも失敗したら、作業用セッションの最後の返答に報告の内容と失敗した理由を書いて止まる（管理用セッションは `list_events` で読める）

## 9. 複数のセッションにまたがる作業は docs で進捗を管理する

複数の Issue に分かれ、いくつかのセッションをまたいで進める作業は、会話や引き継ぎの文章だけでは全体の進み具合を追えなくなる。そのため、`docs/` に進捗の表を持つドキュメントを作って状況を管理する（例: `docs/ai-dev-improvement-plan.md`、`docs/effects-plan.md`）。

- ドキュメントには、方針、項目ごとの状態と Issue / PR の表、進める順番と依存関係を書く。表の上に「◯◯ 時点」の日付を書く
- 状態が変わったら（Issue の作成、PR の作成・マージ、方針の変更）表を更新する。作業用セッションの PR に含めるか、管理用セッションが worktree でまとめて更新する
- ドキュメントを作ったら、CLAUDE.md の「その他のドキュメント」に追加する
- 引き継ぎの文章では、詳しい状況を書かずにドキュメントを示す
