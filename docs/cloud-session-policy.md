# クラウドセッションの基本方針

クラウドセッション（claude.ai/code やスマホアプリから起動する、クラウドのコンテナで動くセッション）で何を任せ、何をしないかの決まり。

## 背景

- 作業は 2 台のマシンで分担している。ロジック担当のマシンはコードとテスト、デザイン担当のマシンはモデリング・エフェクト・UI の見た目を受け持つ。どちらも Unity Editor（と Blender）で検証できる
- クラウドセッションには Unity も Blender も無いため、コンパイル・テスト・動作確認ができない。`.meta` も生成できない
- クラウドセッションは「情報がそろったら進める」という既定の振る舞いを持つ。そのため、2026-11 に Issue の作成を頼んだだけのセッションが、そのままコードの編集まで進めてしまったことがある

## 1. クラウドセッションに任せる作業

| 作業 | 内容 |
|---|---|
| Issue の作成・整理 | Issue の起票、分野ラベルの付与、Issue #66（小さなタスク）のチェックリストの更新 |
| `Management` | CLAUDE.md、スキル、フック、CI、ドキュメント、作業ログ |
| `Spec-Discussion` | 仕様の検証、案出し、`docs/spec/` の更新 |
| 簡素なコード修正 | 下の「簡素なコード修正の範囲」に収まるもの |

上に無い作業（`Design` 全般、Unity / Blender での確認が要る `GameLogic`）は、担当のマシンで行う。頼まれたら引き受けずに、どちらのマシンで行うのがよいかを答える。

### 簡素なコード修正の範囲

次のすべてを満たすものだけを、クラウドで修正してよい。

- 既存の C# ファイルの数か所の修正で済む（定数・条件式の修正、明らかなバグの修正、リネーム、コメントの修正など）
- 新しいファイルを作らない（新しいスクリプトやアセットには Unity が生成する `.meta` が要る）
- `.unity` / `.prefab` / `.asset` / `.inputactions` を編集しない
- 正しさを確かめるのに Play での動作確認が要らない（読めば正しいとわかる、または EditMode テストで確かめられる）

迷うものは修正せずに、ロジック担当のマシンへ回す Issue にする。

## 2. 頼まれた段階で止まる

作業は次の段階に分かれる。**人間が指示した段階までを行い、そこで止まって報告する**。前の段階の指示は、次の段階の許可ではない。

1. 調査・相談（コードや仕様を読んで答える）
2. Issue の作成
3. 実装方針の提示
4. ファイルの編集
5. コミット・push
6. PR の作成

- 「Issue を作って」と頼まれたら、Issue を作って URL を報告して終わる。ブランチの作成やファイルの編集はしない
- 「方針を考えて」「どう直せばいい？」は相談であり、編集の許可ではない。方針を答えて止まる
- 次の段階に進むときは、「〜まで進めてよいか」を尋ね、人間の返答を待つ。返答が無いまま進めない
- 1 つの依頼で複数の段階を頼まれたとき（「Issue を作って実装まで」など）は、その範囲まで進めてよい
- 範囲外の問題に気づいても直さない。Issue #66 のチェックリストへの追加を提案する（追加してよいかも尋ねる）

## 3. コミット・push・PR

- コミットと push は、セッションに割り当てられたブランチ、または人間が指示したブランチにだけ行う
- PR は人間に頼まれたときだけ作る。本文は `.github/pull_request_template.md` に沿い、C# を変更したときは「検証」欄に「未検証（クラウド環境のため）」と書く
- C# を変更した PR は、ロジック担当のマシンでコンパイルとテストを確認してからマージする。そのことを PR 本文と報告に書く

## 4. 報告

- 作業の終わりに、何をしたか（作った Issue・変更したファイル・push したブランチ）と、どの段階で止まったかを短く報告する
- 手元のマシンでの作業が必要なときは、どちらのマシンで何をするかを書く
