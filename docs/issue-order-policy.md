# Issue の実行順序の管理ポリシー

> 作成日: 2026-11-26。Issue が増え、Issue 本文や会話に書いた順番が食い違って混乱しないよう、順番を 1 か所で管理する。セッションが並行して動いても、同じ Issue に 2 つのセッションが着手したり、順番の表が衝突したりしないことを目的にする。

## 1. 置き場所と役割

| 情報 | 置き場所 | 書き込む人 |
|---|---|---|
| Issue の順番と依存関係 | `docs/issue-order.md`（main にあるもの） | 管理用セッション（いなければ人間の指示を受けたセッション 1 つ） |
| 着手中かどうか | GitHub の Issue（`InProgress` ラベルと着手のコメント） | 着手したセッション |
| 完了したかどうか | GitHub の Issue のクローズ | Issue を閉じたセッション |
| 分野ごとの詳しい進捗 | `docs/effects-plan.md`、`docs/sound-plan.md` など | 従来どおり |

- **順番の正は `docs/issue-order.md` だけ**。Issue 本文・分野ごとの docs・会話に書いた順番と食い違ったら、`docs/issue-order.md` に従い、食い違っている側を直す（Issue 本文には「順番は `docs/issue-order.md`」とだけ書けば足りる）
- **状態（着手中・完了）は docs に書かない**。状態は頻繁に変わり、並行するセッションが同じ表を書き換えると衝突するため、GitHub の Issue で管理する。`docs/issue-order.md` は「何をどの順に」だけを持つ

## 2. 順番を読む

- 読むのは **main の最新** の `docs/issue-order.md`。作業ブランチや worktree の中のファイルは古いことがあるので、`git fetch origin main` の後に `git show origin/main:docs/issue-order.md` で読む
- 着手できる Issue は、次をすべて満たすもの
  1. 「先に終わっている必要がある Issue」がすべてクローズしている
  2. `InProgress` ラベルが付いていない
  3. 自分の環境で作業できる（表の「環境」列。CLAUDE.md の「ラベル」）
- 候補が複数あれば、表の上（段階の番号が小さいもの、同じ段階なら上の行）から選ぶ。迷ったら人間に尋ねる

## 3. 着手する（並行するセッションとの取り合いを防ぐ）

着手を決めたら、ブランチを作る前に次を行う（`/issue-start` の手順に含まれている）。

1. Issue を読み直し、`InProgress` ラベルが付いていないことを確認する
2. `InProgress` ラベルを付ける
3. Issue に着手のコメントを書く: `着手: <セッション名または ID> / ブランチ <ブランチ名>`
4. ラベルを付ける直前に別のセッションが付けていた（コメントが自分より先にある）ときは、先に書いたほうが担当する。後から気づいたセッションはラベルを外さずに手を引き、人間（または管理用セッション）に報告する

- 作業を中断するとき（`/suspend-work`）はラベルを付けたままにする。担当をやめるときだけ、ラベルを外してその旨をコメントする
- PR がマージされて Issue がクローズしたら、ラベルを外す
- ラベルが付いたまま長く動きの無い Issue は、管理用セッションが担当のセッションの状態を `get_session` で確かめ、人間に知らせる（勝手にラベルを外さない）

## 4. 順番を変える・Issue を足す

- 順番を決めるのは人間。セッションは案を出し、了承を得てから表を変える
- 表を変えるのは **管理用セッションだけ**（管理用セッションがいないときは、人間が指示したセッション 1 つ）。作業用セッションは自分の PR で `docs/issue-order.md` を変えない。順番に関わる気づき（新しい依存関係など）は、管理用セッションへの報告か PR 本文に書く
- 表の変更は `docs/issue-order.md` だけを変える小さな PR（`Management` ラベル）にし、すぐマージしてもらう。マージされるまでは、変更前の main の順番が有効
- Issue を作ったセッションは、表のどこに入れるかの案を報告に添える。表への追加は上と同じく管理用セッションが行う
- 表の上の「◯◯ 時点」の日付を、変更のたびに更新する

## 5. 表の整理

- クローズした Issue の行は、次に表を変えるときにまとめて消す（消すためだけの PR は作らない）
- 依存先がすべて終わった段階は、下の段階と合わせてよい
- 順番がまだ決まっていない Issue は「未整理」に置き、人間に順番を決めてもらう
